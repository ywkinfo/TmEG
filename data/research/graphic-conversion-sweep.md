# Graphic Conversion Criteria and Repo Sweep Plan

사전 검토 상태: pre-implementation research note

이 문서는 generated JSON이나 파이프라인 규칙을 직접 바꾸기 전, 어떤 콘텐츠를 텍스트로 유지하고 어떤 콘텐츠를 그래픽형 블록으로 승격할지 판단 기준과 전수조사 우선순위를 정리한 메모입니다.

## 목적과 범위

- 목적: 도식형 설명이 평문으로 평탄화되는 사례를 일관된 기준으로 식별하고, repo-wide sweep 순서를 고정한다.
- 범위: PDF 추출 이후 `entry["html"]` 생성 경로에서의 표시 판단을 다룬다.
- 비범위: 원본 PDF 수정, 웹앱 전용 bespoke timeline 컴포넌트 설계, `PLAN.md` 기반 일정 관리.
- 위치 기준: 이 문서는 `data/research/README.md`가 정의한 판단 기록 메모에 해당한다.

## 확인된 문제 요약

현재 리더는 `web/src/components/ReaderArticle.tsx`에서 generated `chapter.html`을 그대로 렌더링한다. 실제 이미지 블록은 `pipeline/common.py`의 `<figure class="reader-image">` 경로를 통해 잘 표현되지만, 도식형 설명이 텍스트 블록으로만 추출되면 그 구조를 복원하지 못한다.

이번 검토에서 확인된 대표 사례는 아래와 같다.

- `data/generated/notebooklm/03-제1부-총칙.md`
  - `《마지막 월에 해당일이 없는 경우 기간의 만료일》`
  - `12월 30일 / 12월 31일 / 2월 28일 / 통지서송달일 / 기 산 일 / 지정기간만료 / 지정기간 2개월`
- `data/generated/notebooklm/03-제1부-총칙.md`
  - `《기간 만료일이 공휴일인 경우 기간연장 기산일》`
  - 날짜와 라벨이 타임라인 구조를 이루지만 현재는 분리된 텍스트 줄로 남아 있다.
- `data/generated/pdf-inventory.json`
  - 해당 페이지는 `imageCount: 0` 계열로 잡혀 실제 image lane을 타지 않는다.
- `tests/test_content_guardrails.py`
  - 짧은 라벨 행은 의도적으로 분리 보존된다. 따라서 일반 텍스트 reflow 규칙을 바꾸는 방향은 회귀 위험이 높다.

## 권장 수정 경계

권장 경계는 **웹앱 렌더러가 아니라 콘텐츠 파이프라인의 HTML 생성 경로**다.

- 유지할 것
  - `entry["text"]`: 검색, excerpt, QA, locator 추적용 평문 기반
  - 짧은 라벨 분리 보존 가드레일
- 바꿀 것
  - `entry["html"]`: 특정 패턴에 한해 synthetic figure, diagram, table-like HTML로 승격

이 경계를 택하는 이유는 다음과 같다.

- 현재 리더는 이미 generated HTML을 주입하는 얇은 shell이다.
- 실제 이미지에 대한 `<figure class="reader-image">` 관용구가 이미 존재한다.
- `build_content.py`는 `text`와 `html`을 별도로 보존하므로 표시 개선과 검색 보존을 분리할 수 있다.
- `blocks_to_text`를 일반 수정하면 다른 정상 텍스트 페이지까지 훼손할 가능성이 크다.

## 그래픽 승격 판단 기준

핵심 질문은 하나다.

> 이 정보가 선형 텍스트로 읽혀도 의미가 보존되는가, 아니면 위치 관계, 좌우 대응, 진행 방향, 박스 grouping이 있어야 의미가 살아나는가.

아래 원칙을 기본값으로 둔다.

- 텍스트 유지
  - 선형 문장이나 항목 리스트로 읽어도 의미가 충분히 보존되는 경우
  - 강조 박스가 있어도 본질이 prose인 경우
- 그래픽 승격
  - 날짜 축, 단계 흐름, 분기, 좌우 비교, boxed case grouping처럼 레이아웃 자체가 의미를 운반하는 경우
  - 평탄화되면 독자가 관계를 다시 추론해야 하는 경우
- 보수 원칙
  - 처음부터 광범위 자동 분류를 하지 않는다.
  - 1차는 allowlist 성격의 고신뢰 패턴부터 시작한다.

## 후보 패턴 분류표

| 패턴군 | 대표 신호 | 기본 분류 | 이유 | 대표 사례 |
|---|---|---|---|---|
| 기간 타임라인 | `《...만료일》`, 연속 날짜, 짧은 라벨, 진행 방향 | 그래픽 승격 우선 | 날짜와 라벨의 상대 위치가 핵심 의미를 가진다 | `03-제1부-총칙.md`의 기간 계산 예시 |
| 절차 흐름도 | `보정`, `재심사`, `분할출원`, `변경출원`, 단계/결과/분기 묶음 | 그래픽 승격 우선 | 처리 순서와 분기 결과가 핵심이다 | `document-data.json`의 재심사/보정/분할/변경 계열 |
| `《...예시》`, `《...사례》` 박스 | boxed title, 다수 라벨, 사례 페어링 | 혼합, 선별 승격 | 일부는 단순 강조문이고 일부는 layout-heavy 예시다 | `pdf-inventory.json`의 요지변경 예시, 간접표시 사례 |
| 비교표/대응표 | 좌우 대응 항목, 제출서류 종류, 판단 비교 | 그래픽 승격 우선 | 열 정렬과 대응 관계가 의미를 이끈다 | 출원상품/보정상품 비교, 소리상표 제출서류 표 |
| 일반 설명문 | 연속 prose, locator 포함 문단 | 텍스트 유지 | 검색성과 원문 추적성이 우선이다 | 대부분의 일반 section 본문 |

## 전수조사 우선순위

### Phase 1. 최고 우선, 고신뢰 그래픽 손실

대상:

- `제4장 기간` 계열 타임라인
- 같은 장 안의 공휴일, 기산일, 만료일, 연장기간 계산 예시

이유:

- 이미 현재 사례에서 손실 양상이 명확하다.
- 도식 의미가 강하고 오탐 가능성이 낮다.

산출물:

- 페이지별 candidate 목록
- synthetic figure 적용 후보와 예외 목록

### Phase 2. 절차 흐름도 계열

대상:

- `재심사의 청구`
- `출원의 보정`
- `출원의 요지변경 및 보정각하`
- `직권보정`
- `분할출원`
- `변경출원`

이유:

- broad sweep에서 단계형 처리 구조가 반복 확인됐다.
- 흐름도를 잘 복원하면 reader 이해도가 크게 오른다.

산출물:

- 단계형, 분기형, 결과형 패턴 세분화
- 흐름도 승격 대상과 텍스트 유지 대상을 구분한 규칙 메모

### Phase 3. `《...예시》`, `《...사례》` callout 계열

대상:

- 요지변경 예시
- 간접적·암시적 표시 사례
- 외국어 약칭 관련 사례
- 대법원 판결 boxed case 요약 등

이유:

- 제목 마커는 강하지만 실제 내용은 prose일 수도 있어 판별이 더 어렵다.

산출물:

- boxed layout가 의미를 가지는 사례와 단순 강조문 사례 분리

### Phase 4. 비교표 및 제출서류 대응표

대상:

- 출원상품/보정상품 대응형 페이지
- 소리상표 제출서류 요구사항 표
- 판단요소 비교형 사례표

이유:

- 비교표는 전용 table-like HTML이 더 맞을 수 있어 패턴 설계가 약간 더 필요하다.

산출물:

- 표형 승격 대상 목록
- comparison/table 계열 전용 처리 규칙 초안

## 1차 탐지 휴리스틱

전수조사 초기에는 아래 신호를 조합한 review queue를 만든다.

- `imageCount == 0`
- `《...》` 형태의 boxed title 존재
- 짧은 날짜/숫자/라벨 행이 연속해서 등장
- 동일 페이지 또는 연속 페이지에 `기산일`, `만료일`, `통지서송달일`, `연장기간`, `예시`, `사례` 같은 패턴이 묶여 있음
- prose보다 label cluster가 더 많음

주의:

- 이 휴리스틱은 자동 적용 규칙이 아니라 **검토 queue 생성용**이다.
- 실제 승격은 chapter/title/page 패턴 기반의 allowlist로 시작한다.

## 가드레일

- `entry["text"]`는 유지한다.
- search, excerpt, locator 기반 추적성을 약화시키지 않는다.
- 짧은 라벨 분리 보존 테스트를 깨지 않는다.
- generated JSON을 수동 편집하지 않고 파이프라인 규칙으로 처리한다.
- 오탐이 의심되는 경우 텍스트 유지가 기본값이다.
- 절차 흐름도 계열 summary figure는 원문을 대체하는 authoritative text가 아니라 reader comprehension을 위한 HTML-only reader aid로 취급한다.
- 절차 흐름도 summary figure를 추가하더라도 같은 section의 원문 prose는 그대로 남겨 두며, search와 locator는 원문 텍스트를 기준으로 유지한다.

## 검증 계획

향후 구현은 아래 검증을 통과해야 한다.

1. 대표 사례 1건 이상에서 `entry["html"]`만 figure/diagram 형태로 바뀌고 `entry["text"]`는 유지된다.
2. 기존 이미지 블록 `<figure class="reader-image">` 경로와 충돌하지 않는다.
3. `npm run content:prepare`와 `npm run content:qa`가 통과한다.
4. 검색 결과 excerpt와 locator가 구현 전과 동등 수준으로 유지된다.
5. 고신뢰 텍스트 페이지에서 오탐 승격이 발생하지 않는다.

## 열린 질문

- `《...예시》`, `《...사례》` 계열 중 어디까지를 그래픽 승격 대상으로 볼지
- 비교표 계열을 기존 figure 관용구로 수용할지, table-like HTML을 별도 둘지
- 모바일에서 타임라인과 비교표를 어떤 최소 readable 형태로 둘지

이 문서는 구현 계획서가 아니라 판단 기준 메모다. 실제 규칙 추가와 검증 순서는 후속 implementation note 또는 commit diff에서 관리한다.
